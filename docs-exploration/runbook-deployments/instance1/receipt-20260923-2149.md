## Attempt Log

### Attempt 1: Tool Prerequisites & Non-Interactive GKE Provisioning
- **What Failed:** The initial `deploy.sh` script failed because required tools (`helm`, `ko`, `podman`) were missing on the runner system. Additionally, the GKE cluster creation would prompt the user for zone options in a headless environment, causing a hang.
- **Evidence:** `helm: command not found`, `ko: command not found`, `gcloud` prompting for zonal selections.
- **What was changed:** 
  1. Installed Helm 3, `ko` CLI (via go install), and `podman` (via apt-get).
  2. Modified GKE cluster creation and credentials fetching in `deploy.sh` to explicitly target zone `us-central1-a` (matching other VMs in the project), guaranteeing non-interactive execution.
  3. Replaced local `make push-task-runner` with local Go cross-compilation and Google Cloud Build submission (`gcloud builds submit`), which cleanly packages and pushes the image remotely without requiring a local Docker/Podman daemon.
  4. Added checks to make GKE, GCS, and GSA provisioning fully idempotent and re-runnable.

### Attempt 2: GCP IAM Replication Delay
- **What Failed:** Submitting the IAM bindings immediately after service account creation failed because of transient replication delays across GCP's global identity directory.
- **Evidence:** `ERROR: (gcloud.storage.buckets.add-iam-policy-binding) HTTPError 400: Service account ... does not exist.`
- **What was changed:** Introduced a `sleep 15` replication delay and a robust `retry_cmd` shell helper in `deploy.sh` that wraps and retries all `gcloud` IAM policy bindings up to 10 times.

### Attempt 3: Lack of ClusterTrustBundle Support in GKE
- **What Failed:** The `ax-controller` pod crashed on startup because GKE standard clusters do not support the Kubernetes `ClusterTrustBundle` API. The projected volume `servicedns-ca` was empty, causing `ax-controller` to fail to find the CA certificate.
- **Evidence:** `failed to initialize substrate client error="reading CA file \"/run/servicedns-ca/trust-bundle.pem\": no such file or directory"`.
- **What was changed:** 
  1. Modified `deploy/ax-controller.yaml` to mount `servicedns-ca` from a standard local ConfigMap instead of `clusterTrustBundle`.
  2. Added a ConfigMap replication step in `deploy.sh` that copies the Substrate `ateapi-ca` ConfigMap from the `ate-system` namespace into the `ax-system` namespace, utilizing `jq` to strip system metadata and avoid conflict errors on re-runs.

### Attempt 4: GKE JWT Issuer Verification Failure
- **What Failed:** Submitting tasks via the compiled `ax` CLI resulted in an authentication failure because the Substrate API server rejected GKE's default service account OIDC issuer.
- **Evidence:** `rpc error: code = Unauthenticated desc = invalid bearer token: unexpected issuer ...locations/us-central1-a/clusters/ax-instance1-gke`.
- **What was changed:** Modified the Helm upgrade command in `deploy.sh` to configure `auth.jwt.issuer` explicitly with the cluster's real GKE OIDC discovery endpoint.

### Attempt 5: Worker Pool Certificate & gVisor Capability Restrictions
- **What Failed:** Sandboxed actor execution failed to verify because no WorkerPools existed. After creating worker pools, the workers failed to boot due to missing certificate bundles, invalid private key PEM types (`RSA PRIVATE KEY` vs `PRIVATE KEY`), and missing custom SPIFFE `PodIdentity` extensions on our self-signed certificates. Finally, gVisor process checkpointing failed with `exit status 128` because the workers lacked root process capabilities and the GCS storage backend was mapped to the in-cluster S3-compatible RustFS.
- **Evidence:** `no free workers available`, `unknown PEM block type "RSA PRIVATE KEY"`, `worker certificate has no valid Pod identity`, `runsc checkpoint: exit status 128`, `NoSuchBucket: The specified bucket does not exist`.
- **What was changed:** 
  1. Compiled and pushed a matching `ateom-gvisor` image from the exact Substrate commit `672533541dbf` pinned in `go.mod`.
  2. Generated self-signed certificates in Go with the custom OID `1.3.6.1.4.1.11129.2.12.1` extension and a JSON-marshaled `PodIdentity` block, converting the private key to PKCS#8 `PRIVATE KEY` format via `openssl`.
  3. Created independent `default-workerpool-deployment` deployments in both namespaces (releasing them from `WorkerPool` ownership to prevent controller reversions) containing `securityContext.privileged: true` to grant them CRIU process capabilities.
  4. Configured the correct downwardAPI `capacity-volume` to project CPU and memory resources, and disabled OpenTelemetry SDK/Detectors (`OTEL_SDK_DISABLED=true`, `OTEL_EXPERIMENTAL_RESOURCE_DETECTORS=none`) to avoid GKE metadata server hangs.
  5. Updated the templates to target the in-cluster S3-compatible RustFS bucket `gs://ate-snapshots/`.
